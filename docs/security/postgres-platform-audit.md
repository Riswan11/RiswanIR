# PostgreSQL preview audit inventory

Baseline is PR #40 squash commit `783d4bc`. The hosted preview is limited to development and testing. This inventory identifies the repository of record by domain. A request can produce a security authorization decision, a resource lifecycle event and a receipt, each with a different purpose.

| Domain and authority | PostgreSQL persistence and scope | Access and transaction boundaries |
| --- | --- | --- |
| Identity, browser sessions and workload lifecycle. `identity_repository.py` and `postgres_identity.py` | `riswan_auth.authentication_events` and `identity_status_history`. Identity and actor scope includes pre-tenant events. Browser session and workload enrollment rows hold current state. | Identity runtime uses restricted access under migration 0013. Identity revocation and required audit persist together. Authentication data is excluded from tenant timelines. |
| Authorization and role administration. `authorization_repository.py` and `postgres_control.py` | `riswan_control.authorization_audit_events`. Records actor, tenant, action, resource, outcome, reason and policy version. | Evaluator records denies and privileged allows. Required audit failure denies access. Control runtime has append access under migration 0014. |
| Organizations, tenant lifecycle, membership and invitations. `tenancy.py` | `riswan_control.organization_audit_events`. Tenant-bound records carry event ID, actor, operation, target, request and time. | Control transaction includes required lifecycle audit. The new audit API requires current organization permission and MFA. It projects only timeline fields and verifies cursor ownership. |
| Secrets, versions, rotation, revocation, cloud credentials and provider binding. `secrets.py`, `postgres_control.py` and the platform secrets service. | `riswan_control.secret_access_events`. Tenant and product scope includes workload and provider context where applicable. Provider instances, bindings, lease and rotation state live in control tables. | Control role and forced RLS apply under migration 0015. Audit stores outcomes and authorized references. | Integration and collection. `postgres_collections.py` and hosted collection routes. | `riswan_data.collection_runs` is an operational receipt scoped to tenant, product and integration. | Protected-object mutations. `postgres_objects.py` | `riswan_data.protected_object_audit` records object UUID, scope, actor and actor type, request, correlation and database time. | Restricted product role has column-level insert and forced RLS. | Legal holds. `postgres_cases.py` | `riswan_data.investigation_hold_audit` records case and scoped actor attribution alongside hold state. | Authorized product transaction owns the mutation and history under migration 0005. |
| Investigation and analyst history. `postgres_cases.py` | `riswan_data.case_memory_history` preserves investigation memory feedback and retrieval history. Case custody and evidence revisions preserve evidence lineage in the product domain. | Product RLS and scoped investigation routes apply. Investigation custody establishes evidence lineage. It has a separate purpose from platform access auditing. |

The migration role owns the tables. Runtime roles are separate and lack ownership and BYPASSRLS. The application establishes transaction-local scope on pooled connections. A holder of runtime database credentials can set custom PostgreSQL scope settings, so treating those credentials as trusted remains part of the deployment boundary. Append-only runtime privileges provide protection against rewriting or deleting recorded events. Privileged administrators retain database-level control. Retention, legal-hold-aware disposal and verified erasure remain Checkpoint C.

Workstation SQLite remains available under its explicit configuration. The fully PostgreSQL preview composes PostgreSQL identity, tenancy, authorization and product repositories. The compatibility configuration selecting SQLite controls must be assessed separately from a PostgreSQL outage. The investigation compiler also uses ephemeral SQLite staging. Application logs remain operational diagnostics.

## Acceptance work

The tenant timeline currently covers organization events and request filtering. An authenticated product, actor, workload, integration and resource audit retrieval design needs separate permissions and bounded query verification. Organization, control and product connections have separate transactions. A control success audit records authorization to attempt a product operation. Product receipts, hold history and protected-object audit record committed effects within their product transactions. Administrative integration enable/disable changes and future configuration update paths need separate lifecycle audit and rollback verification. Broader identity and collection receipt retrieval, administrative changes outside the preview application, and the full cross-subsystem correlation and query-plan matrix remain acceptance work.

## Tenant timeline query plan

A disposable CI fixture added 256 tenant records and queried through the restricted control role with matching control and audit-read scope. PostgreSQL used a bitmap index scan on `organization_audit_timeline`, a bitmap heap scan, and a top-N sort on `occurred_at DESC, id DESC`. The scoped scan produced 260 rows and the limit returned 25. The index supports tenant filtering and the chronological key used by pagination. This run used PostgreSQL's default planner settings and is evidence for this fixture only.

## Control and product registration sequence

The hosted route authorizes enrollment and stages provider and workload bindings in the control transaction. The binding insert and its structured security event share a savepoint. The product connection inserts the registration and its trigger-generated event, then commits independently. Control authorization remains locked through registration and window reservation. If the control commit fails after registration, the durable registration event still represents a product commit. Hosted fault tests cover denial before publication, required binding audit failure, product rollback after writing registration audit, and a control failure after product registration. Restart retries verify a single product registration audit. Subsequent attempts verify the exact persisted registration and current enrollment before credential issuance and revalidate ownership before publishing.

The tenant API applies actor, resource, operation, UTC time bounds and request filters only inside the authorized tenant. The cursor record must exist within the selected tenant and match the supplied predicates. Secret resource audit already uses the separate SECRET_AUDIT permission and a product-scoped transaction. Credential events are excluded from secret-resource audit even when the identifiers coincide. The tenant timeline has no read path into pre-tenant authentication history.

| Additional audit distinction | Authoritative storage and access |
| --- | --- |
| Membership, invitations and workload roster enrollment/revocation | Tenant control writes and audit use the organization transaction. Actor, target and request ID are captured. Tokens are excluded from the timeline. |
| Workload identity status changes | Identity status history records the platform actor and status. Identity runtime appends and tenant administrators have no read entitlement. |
| Credential binding creation | Control secret access events record trusted workload, integration, provider identifier, operation, outcome, request and correlation. The binding and event commit together. Registry and connector inputs are excluded. |
| Secret provider binding | Existing secret bind operations use the scoped secret lifecycle contract and audit records. Runtime scope requires tenant and product, and secret retrieval uses SECRET_AUDIT. |
| Collection configuration and enablement | Initial configuration is persisted with registration. The runtime has no administrative configuration, enablement or removal API for this preview. Privileged direct database enablement changes are outside the application audit role. |
| Collection attempts and outcomes | Collection runs retain bounded counts, status and correlation. They are publication receipts. Workload credentials have a separate audit authority. |

The internal PostgreSQL credential audit service uses the existing SECRET_AUDIT authority and requires tenant, product and integration scope. It supports workload, operation, outcome, time, request and correlation predicates. Credential cursors are resolved inside the same selected scope. An invalid or foreign cursor yields an empty page. Integration receipts and pre-tenant identity history retain separate authorities. The credential plan fixture adds 256 matching issuance events and executes the service statement under the control role, using all ownership and credential event predicates.
